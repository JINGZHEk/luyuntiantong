# 路云天瞳夜间真实路口大屏视觉恢复设计

## 1. 背景与目标

当前 `zhiluwujie` 页面已经具备实时 WebSocket 数据接入、场景数据驱动、动态目标对象池和 16 个 SQLite 演示场景，但视觉层在后续 daylight 重构中被替换成了浅色低对比度风格。用户确认的目标是恢复此前已经实现过的深色夜间路口效果：深色道路、路口建筑、车辆与信号灯、斑马线、暖色窗光、克制的 HUD，以及具有电影感的空间层次。

本设计只恢复和增强 3D 大屏的视觉表现，不回退当前的数据链路。最终结果应满足：

1. 大屏默认呈现用户提供截图中的夜间真实路口风格。
2. WebSocket、16 个场景、SQLite mock 数据、实时对象池和事件展示继续可用。
3. 车辆、行人、非机动车和信号灯的运动由实时数据或 fallback 状态驱动，不再由视觉层自行生成一套互相冲突的状态。
4. 目标位置更新连续，10 Hz 左右的数据到达频率下不出现明显瞬移或抖动。
5. 在常用 1920×1080 展示分辨率下保持稳定渲染；视觉效果不能以牺牲交互和数据更新为代价。

## 2. 目标视觉基线

以用户提供的旧版截图为唯一视觉基线。截图中的风格是“克制的夜间数字孪生”，不是高饱和霓虹赛博朋克，也不是浅色白天仿真。

### 2.1 场景色彩

| 层级 | 目标表现 |
| --- | --- |
| 天空与远景 | 近黑蓝色，保留轻微雾化层次，不使用纯黑导致物体丢失 |
| 车道与路面 | 接近黑色的冷蓝灰，具有很弱的粗糙度变化和阴影承接 |
| 人行道与建筑 | 深灰蓝，明度略高于道路，用轮廓分离空间 |
| 车道线与斑马线 | 车道线使用低饱和暖金色，斑马线使用偏暖灰白色 |
| 建筑窗光 | 暗金色小面积发光，作为远景空间尺度提示 |
| 风险提示 | 只在有风险时使用橙红色，避免全屏持续发光 |
| HUD | 深色半透明面板，文字以灰白、低饱和青色和金色为主 |

视觉参数的默认值集中在 `frontend/src/pages/zhiluwujie/sceneVisuals.ts`，页面 CSS 只消费这些语义化变量，不在多个文件内重复定义颜色。

### 2.2 空间构图

- 保留高位斜俯视摄像机，视点覆盖交叉口中心、至少一个远端建筑立面和前景道路。
- 保留用户截图中的道路比例、路口尺度、车道线方向和斑马线关系。
- 前景车辆和事件目标应位于视觉焦点区域；远景交通只用于提供密度和尺度，不抢占事件信息。
- HUD 面板沿屏幕边缘布置，避免遮住路口中心和主要事件目标。
- 相机仍支持 OrbitControls，但默认视角必须直接进入可汇报展示的构图。

### 2.3 3D 对象质感

第一阶段继续使用项目内程序化 Three.js 模型，不引入外部 GLB 资产和新的版权依赖。程序化模型要从“单一发光方块”提升为可辨识的交通参与者：

- 小客车：车身、车舱、车轮、前后灯和简单玻璃分层，车身保持哑光金属质感。
- 公交车/货车：通过车身尺寸、驾驶舱和货厢/车窗分层区分，不与小客车共用同一盒体外观。
- 行人：身体、头部和腿部形成低面数轮廓，并根据遮挡等级改变透明度和边缘提示。
- 自行车/电动车：车轮保持竖直，车架和骑手分离，转向与运动方向一致。
- 交通信号灯：灯杆、灯箱、灯色发光面和地面投影分开渲染。
- 目标高亮：仅对当前风险目标使用轮廓、地面环或轨迹线；普通目标不使用持续霓虹描边。

## 3. 架构与数据边界

### 3.1 保留的数据链路

```text
后端 demo / 未来真车端
        ↓ WebSocket
sceneRealtimeAdapter
        ↓ perception / vehicle_status / decision / event
ZhiluWujieScene
        ↓
SceneObjectPool + fallback state machine
        ↓
Three.js 夜间路口渲染
```

视觉恢复不得修改 MQTT、Cloud API、WebSocket 消息类型和 STGNN 数据协议。`sceneRealtimeAdapter` 继续负责判断当前是 `live` 还是 `fallback`，`ZhiluWujieScene` 继续接收现有的 perception、vehicle status、decision 和 event payload。

### 3.2 实时目标与 fallback

- WebSocket 有有效消息时，动态车辆、行人和非机动车由 `SceneObjectPool` 管理，目标数量、类别、坐标、航向、速度和遮挡等级来自 payload。
- WebSocket 暂时断开或没有有效 frame 时，保留现有 fallback 场景循环，确保大屏不黑屏；HUD 必须明确显示 `FALLBACK`，不能伪装成实时数据。
- 同一目标只允许存在一份视觉实例。实时模式切换时清理旧模式的对象或隐藏旧模式组，避免重影。
- 超过 TTL 的目标销毁模型并释放 geometry/material；短暂丢帧不能立即造成视觉闪烁。

### 3.3 坐标与运动平滑

继续使用 `sceneCoordinates.ts` 完成米制道路坐标到 Three.js 坐标的转换。对象池将每个目标拆成“数据目标状态”和“渲染显示状态”：

1. 收到 payload 时更新目标位置、航向、速度和 `lastSeenAt`。
2. 每个渲染帧根据目标状态进行位置和航向插值，使用基于 delta time 的平滑系数，避免帧率变化造成速度变化。
3. 目标短时无新数据时按最近速度做有限预测，预测窗口受 TTL 限制，不能无限外推。
4. 收到新场景或 run 时清空上一场景的插值缓存，避免跨场景拖影。

该机制只改变显示方式，不改变上报数据和风险计算结果。

## 4. 渲染与性能方案

### 4.1 光照与后处理

- 使用低强度冷色环境光、低角度方向光和少量局部车灯/窗光，恢复夜间明暗关系。
- 保留阴影，但将阴影质量设置为展示设备可承受的默认档；大型屏幕或高性能设备允许提高档位。
- 保留 UnrealBloomPass 作为可调效果，默认使用克制的低强度，只让信号灯、车灯和风险提示产生轻微光晕。
- 使用 ACES tone mapping 统一高光，避免当前 daylight 版本中大面积灰白背景压平对比度。
- 扫描线、粒子和覆盖范围只作为辅助层，默认透明度低，不得成为画面主体。

### 4.2 帧率与 UI 更新

- WebGL 像素比设置上限，默认优先稳定帧率；展示设备性能较好时再提高分辨率。
- 阴影贴图、Bloom 和粒子数量使用固定的展示档位，不在每帧重新创建资源。
- Three.js 动画循环只负责场景更新和渲染；React HUD 维持低频刷新，避免每帧触发大量状态更新。
- 吞吐量曲线使用已有数据或受控采样，不在每个 UI tick 生成一组随机值，避免视觉噪声和不必要的重渲染。
- 目标模型、材质和几何体由对象池复用；只有类别变化或目标销毁时才替换/释放模型。

## 6. 错误处理与降级

- WebSocket 断开：显示 `FALLBACK`，继续渲染 fallback 场景，并保留最后一帧的合理状态。
- 单条 perception 数据字段缺失或坐标非法：忽略该目标，不影响其他目标和渲染循环。
- 目标短时消失：在 TTL 内保持平滑状态，超过 TTL 后移除并释放资源。
- WebGL 后处理不可用：退回直接 renderer 渲染，场景仍可展示；HUD 继续工作。
- 场景切换或 run 重置：先清理实时对象、插值缓存和旧轨迹，再载入新场景，防止旧目标残留。

## 7. 验证方案

### 7.1 自动化验证

- 更新 `sceneVisuals.test.ts`，验证夜间默认背景、Bloom 和扫描线参数处于目标范围。
- 为 `SceneObjectPool` 增加测试：目标 upsert、坐标映射、插值更新、TTL 删除、类别切换和资源清理。
- 保留现有 realtime adapter 与数据协议测试，确认视觉恢复没有改变 live/fallback 判断。
- 执行前端类型检查、单元测试和生产构建。

### 7.2 浏览器验收

在 `http://127.0.0.1:3011/zhiluwujie` 验证：

1. 进入后默认看到深色夜间交叉口，视觉构图接近用户提供截图。
2. 启动 16 个场景时，车辆、行人、非机动车数量和运动轨迹随数据变化。
3. 实时 WebSocket 连接时显示 live 数据；断开后自动 fallback，画面不黑屏。
4. 风险目标出现时只对目标区域增强，不出现全屏高亮污染。
5. 拖动相机、切换四种模式和切换场景时无明显卡顿、重影或白屏。
6. 1920×1080 下连续运行 5 分钟，目标移动不明显抖动，浏览器控制台无新增错误。

## 8. 不在本次范围内的内容

- 不修改后端 API、MQTT topic、WebSocket payload 和 STGNN 模型。
- 不重新设计监控、事件回放和模型评估页面。
- 不引入外部 3D 模型、纹理包或需要额外下载的资源。
- 不把 fallback 标记隐藏成“真实在线”，数据来源仍然如实显示。
- 不改变 16 个场景的业务逻辑；仅让它们使用统一的夜间视觉和数据驱动渲染。

## 9. 完成标准

当夜间场景在视觉上恢复到用户截图的构图与质感，同时实时数据、fallback、16 个场景、动态对象池和现有 HUD 功能均通过上述验证，且前端构建和测试通过，本设计视为完成。
