# 分布式多智能体车路协同遮挡感知平台 —— "仿真优先"完整实施方案

------

## 1）仿真优先路线总览（Why + What）

### Why：为什么先仿真是最优路径

| 维度     | 先仿真                                   | 先实体                               |
| -------- | ---------------------------------------- | ------------------------------------ |
| 成本     | 仅需开发机，零硬件采购                   | Jetson + 小车 + 路侧相机，￥5k+      |
| 迭代速度 | 改代码→秒级重跑                          | 改代码→烧录→布线→跑场→收数据，小时级 |
| 安全风险 | 零碰撞风险                               | 制动逻辑 bug → 小车撞墙/伤人         |
| 可复现性 | 同一 seed 完美复现                       | 光照、电量、网络抖动均不可控         |
| 团队并行 | 前端/算法/云端可各自用 mock 数据独立开发 | 所有人排队等实体平台                 |
| 答辩演示 | 可录屏、可回放、可调参数做 AB 对比       | 实体演示"翻车"概率高                 |

**核心结论**：仿真阶段的目标是**验证算法逻辑与系统架构的正确性**，而非追求传感器级真实感。只要接口协议与数据格式对齐实体平台，迁移成本极低。

### 本阶段不做什么（防止范围膨胀）

| 明确排除项                    | 原因                                 |
| ----------------------------- | ------------------------------------ |
| 不购买/调试任何硬件           | M0-M2 纯软件闭环                     |
| 不训练大规模 GNN（>50M 参数） | 先用轻量检测 + 线性预测跑通链路      |
| 不接入真实 GPS/IMU            | 用数据集坐标系或仿真坐标系           |
| 不做多路侧节点融合            | 先单路侧跑通，多节点是 M3+           |
| 不做 V2X 标准协议（BSM/RSM）  | MQTT 自定义 Topic 足够，迁移时再封装 |
| 不做移动端/小程序             | 仅 Web 前端                          |

### 阶段里程碑

| 里程碑         | 目标                               | 时间     | 交付物                          |
| -------------- | ---------------------------------- | -------- | ------------------------------- |
| **M0**         | 单帧检测 → MQTT → 前端渲染闭环     | Week 1   | 可运行 demo，3 分钟演示视频     |
| **M1**         | 时序预测 + TTC 风险判定 + 事件回放 | Week 2-3 | 完整评测报告，预测精度达标      |
| **M2**         | 多场景批量评测 + 云端孪生完善      | Week 4   | 可答辩的完整系统 + 论文实验数据 |
| **M3**（后续） | Jetson 部署 + 实体小车联调         | Week 5-8 | 实体演示视频                    |

## 2）系统架构（纯虚拟边-端-云）

### 模块架构文字描述

### 各模块详细定义

#### A. Roadside Sim Agent（路侧感知仿真智能体）

| 属性         | 描述                                                         |
| ------------ | ------------------------------------------------------------ |
| **输入**     | DAIR-V2X 图像帧 + 标注（按时间戳顺序回放）；遮挡区域 mask（由 BEV 投影计算） |
| **输出**     | 检测框 + 类别 + 置信度；轨迹预测点序列（未来 1-3 秒）；遮挡风险标签 |
| **依赖**     | Python 3.10+, PyTorch, ultralytics(YOLOv8), MQTT client      |
| **失败模式** | ① 数据文件缺失 → 跳帧并记录 warning ② 检测延迟 >100ms → 标记 degraded 状态 ③ MQTT 断连 → 本地缓存 + 指数退避重连 |

#### B. Vehicle Decision Agent（车端决策仿真智能体）

| 属性         | 描述                                                         |
| ------------ | ------------------------------------------------------------ |
| **输入**     | 路侧共享的检测+预测结果（via MQTT）；自车仿真状态（位置/速度/航向） |
| **输出**     | 风险等级（safe/warning/danger/emergency）；制动指令（减速度值）；决策日志 |
| **依赖**     | Python 3.10+, MQTT client, NumPy                             |
| **失败模式** | ① 路侧消息超时（>200ms） → 启用纯自车感知降级模式 ② TTC 计算除零 → 夹紧最小速度阈值 0.1m/s ③ 状态机异常 → 强制进入 emergency_stop |

#### C. Cloud Twin Agent（云端孪生智能体）

| 属性         | 描述                                                         |
| ------------ | ------------------------------------------------------------ |
| **输入**     | 所有 MQTT Topic 的消息流                                     |
| **输出**     | REST API 供前端查询；事件检索结果；统计报表                  |
| **依赖**     | FastAPI, TimescaleDB（仿真阶段可用 SQLite 替代）, MQTT client |
| **失败模式** | ① 数据库写入失败 → WAL 模式 + 本地 JSON 备份 ② API 超时 → 返回最近缓存数据 + stale 标记 |

#### D. Frontend（Three.js 前端）

| 属性         | 描述                                                         |
| ------------ | ------------------------------------------------------------ |
| **输入**     | MQTT 实时消息（WebSocket 桥接）；Cloud API 历史数据          |
| **输出**     | 3D 可视化渲染；用户交互指令（回放控制、视角切换）            |
| **依赖**     | Three.js, MQTT.js, 已有前端基础                              |
| **失败模式** | ① WebSocket 断连 → 显示连接状态 + 自动重连 ② 帧率过低 → LOD 降级 + 减少渲染对象 |

### 同步机制

| 项目         | 方案                                                         |
| ------------ | ------------------------------------------------------------ |
| **时钟基准** | 数据集帧时间戳（Unix epoch ms），所有模块使用同一时间戳字段 `ts_ms` |
| **帧同步**   | 路侧按固定帧率（10Hz）回放，每帧附 `frame_id` + `ts_ms`，车端/云端/前端均以 `frame_id` 对齐 |
| **因果顺序** | 路侧感知 → 车端决策 → 云端存储 → 前端渲染，严格单向流；车端等待路侧消息到达后再计算 |
| **延迟模拟** | 可配置人工延迟 `sim_latency_ms`（默认 0），用于测试通信延迟对决策的影响 |
| **心跳**     | 每个 Agent 每 5 秒发送 heartbeat 到 `v2x/heartbeat/{agent_id}`，Cloud 监控在线状态 |

## 3）通信协议与 Topic 设计（MQTT）

### Topic 列表与 Payload 定义

#### Topic 1: `v2x/roadside/{node_id}/detection`

路侧检测结果（每帧发布）

#### Topic 2: `v2x/roadside/{node_id}/prediction`

路侧轨迹预测结果

#### Topic 3: `v2x/vehicle/{vehicle_id}/status`

车端自车状态

#### Topic 4: `v2x/vehicle/{vehicle_id}/decision`

车端风险决策结果

#### Topic 5: `v2x/event/{event_type}`

高危事件通知（云端消费用于检索和回放）

#### Topic 6: `v2x/heartbeat/{agent_id}`

心跳与健康状态

#### Topic 7: `v2x/control/playback`

前端 → 后端的回放控制指令

#### Topic 8: `v2x/roadside/{node_id}/occlusion_zone`

路侧遮挡区域估计

### Schema 版本管理策略

| 策略         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| **版本号**   | 语义化版本 `MAJOR.MINOR.PATCH`；MAJOR 改=不兼容，MINOR 改=新增字段，PATCH=修正描述 |
| **前向兼容** | 消费者忽略未知字段（`additionalProperties: true`）；必填字段仅在 MAJOR 版本添加 |
| **后向兼容** | 新增字段必须有默认值；弃用字段先标 `deprecated` 保留两个 MINOR 版本再删 |
| **校验**     | 每个 Topic 对应一个 JSON Schema 文件存于 `schemas/` 目录；CI 可做 payload 校验 |
| **协商**     | Agent 启动时在 heartbeat 中上报自己支持的 `schema_version`，Cloud 记录兼容性矩阵 |

## 4）数据与场景构建（基于 DAIR-V2X）

### 从 DAIR-V2X 切 Mini Split

| 步骤        | 操作                                                         | 产出               |
| ----------- | ------------------------------------------------------------ | ------------------ |
| 1. 下载     | DAIR-V2X-I（路侧数据集）或 DAIR-V2X-C（协同数据集），选 Intersection 子集 | 原始数据           |
| 2. 筛选     | 脚本 `filter_pedestrian_scenes.py`：过滤包含 `pedestrian` 标注且存在遮挡标记的帧序列 | 候选序列列表       |
| 3. 切片     | 每个序列取连续 50-100 帧作为一个 clip                        | ~30-50 个 clips    |
| 4. 划分     | 70% train / 15% val / 15% replay（replay 集选最有代表性的场景用于演示） | 三个子集           |
| 5. 标注增强 | 对 replay 集人工补充遮挡等级标签（light/moderate/heavy）     | 增强标注           |
| 6. 格式转换 | 统一转为项目内部格式（见下方）                               | `mini_split/` 目录 |

**内部数据格式**：

### 3 类遮挡难度场景设计

| 场景级别     | 名称       | 遮挡率 | 描述                                                | 代表案例                               |
| ------------ | ---------- | ------ | --------------------------------------------------- | -------------------------------------- |
| **Light**    | 半遮挡缓行 | 20-40% | 行人被路侧灌木/电线杆部分遮挡，上半身可见，匀速直行 | 行人沿人行道行走，被花坛遮挡下肢       |
| **Moderate** | 车后穿行   | 40-70% | 行人被停放车辆遮挡大半，有横穿意图，速度中等        | 典型"鬼探头"前兆：行人在停车间隙中探头 |
| **Heavy**    | 突然冲出   | 70-95% | 行人被大型车辆完全遮挡，突然快速冲入车道            | 儿童从公交车前方跑出，几乎无预警       |

### "鬼探头"事件标签规范

| 字段                      | 定义                                                         |
| ------------------------- | ------------------------------------------------------------ |
| `trigger_frame`           | 行人首次从遮挡区域进入车道的帧 ID                            |
| `pre_trigger_frames`      | trigger_frame 前 10 帧（用于预测模型训练）                   |
| `risk_window_start`       | 行人进入自车行驶车道的帧                                     |
| `risk_window_end`         | 行人离开自车行驶车道 OR 自车完全停止 OR 碰撞发生             |
| `ttc_at_trigger`          | trigger_frame 时刻的 TTC 值（秒）                            |
| `occlusion_level`         | light / moderate / heavy                                     |
| `pedestrian_speed`        | 行人进入车道时的速度（m/s）                                  |
| `end_condition`           | `avoided`（成功避让）/ `collision`（碰撞）/ `timeout`（超出观测窗口） |
| `ground_truth_trajectory` | 行人在 risk_window 内的真实轨迹点序列                        |

## 5）算法最小可行方案（MVP）

### 执行顺序与验收标准

### Phase A：检测 + 硬阈值（Day 1-2）

#### 路侧感知

| 项目     | 方案                                                         |
| -------- | ------------------------------------------------------------ |
| 检测模型 | YOLOv8-nano（ultralytics 直接加载预训练权重，不训练）        |
| 输入     | DAIR-V2X 图像帧（按 10Hz 回放）                              |
| 输出     | 2D bbox + 类别 + 置信度 → 通过标定矩阵投影到 BEV 坐标 → 发布到 MQTT |
| 遮挡判定 | 初版：bbox 面积 / 同类平均面积 < 阈值 → 标记为遮挡（简单但有效） |

**验收标准**：在 replay 集上，行人检测 recall > 0.7，前端能实时显示检测框。

#### 车端决策

| 项目     | 方案                                                         |
| -------- | ------------------------------------------------------------ |
| 风险计算 | TTC = 自车到目标距离 / 相对接近速度                          |
| 决策逻辑 | TTC > 4s → safe; 2-4s → warning; 1-2s → danger(减速); <1s → emergency(急停) |
| 输出     | 风险等级 + 制动指令 → MQTT                                   |

**验收标准**：给定一组已知 TTC 的 mock 数据，决策输出 100% 符合规则表。

#### 云端

| 项目 | 方案                                               |
| ---- | -------------------------------------------------- |
| 存储 | SQLite + 按 frame_id 索引                          |
| API  | 一个 `/api/frames/{frame_id}` 接口返回该帧所有数据 |

**验收标准**：可通过 API 查询任意帧数据，响应 < 100ms。

### Phase B：轨迹预测 + 多级规则（Day 3-4）

#### 路侧轨迹预测

| 项目     | 方案                                                         |
| -------- | ------------------------------------------------------------ |
| 模型     | 线性外推（Constant Velocity Model）：用过去 5 帧位置做线性回归，外推未来 3 秒 |
| 输入     | 历史轨迹缓存（每个 obj_id 保留最近 10 帧位置）               |
| 输出     | 未来 6 个时间步的预测坐标 + 置信度（随时间递减）             |
| 遮挡增强 | 对遮挡目标增加横向速度不确定性（±30%），生成多条候选轨迹     |

**验收标准**：在 val 集非遮挡场景上，1 秒 ADE < 0.5m。

#### 车端增强决策

| 项目 | 方案                                                       |
| ---- | ---------------------------------------------------------- |
| 融合 | 接收路侧预测轨迹，计算所有预测点与自车预测位置的最小距离   |
| 规则 | 在 TTC 基础上增加：预测碰撞概率 > 0.5 → 提前一级预警       |
| 降级 | 路侧消息丢失 > 3 帧 → 切换到纯自车 TTC 模式 + 增大安全余量 |

**验收标准**：在 moderate 遮挡场景中，预警时间比 Phase A 提前 > 0.5 秒。

### Phase C：GNN 预测 + 回放系统（Day 5-7）

#### 路侧 GNN 预测（如时间允许，否则保持线性预测）

| 项目     | 方案                                                         |
| -------- | ------------------------------------------------------------ |
| 模型     | 轻量时空图网络：节点=检测目标，边=空间邻近关系；2 层 GCN + 1 层 GRU，参数 < 1M |
| 训练     | 在 mini_split/train 上训练，DAIR-V2X 标注作 GT，batch_size=16，epochs=30 |
| 损失函数 | ADE Loss + 遮挡感知加权（heavy 遮挡样本权重 ×3）             |

**验收标准**：在 heavy 遮挡场景 1 秒 ADE < 0.8m，优于线性外推。

#### 云端回放

| 项目     | 方案                                                        |
| -------- | ----------------------------------------------------------- |
| 事件检索 | `/api/events?severity=critical&limit=10`                    |
| 回放     | `/api/replay/{event_id}` 返回该事件所有帧数据，前端逐帧渲染 |

**验收标准**：可选中任意高危事件，前端完整回放过程。

## 6）评测体系与指标口径

### 感知指标

| 指标                       | 公式                                      | 目标值                    |
| -------------------------- | ----------------------------------------- | ------------------------- |
| **检测精确率 (Precision)** | TP / (TP + FP)，IoU ≥ 0.5 为正确          | > 0.80                    |
| **检测召回率 (Recall)**    | TP / (TP + FN)                            | > 0.75（遮挡目标 > 0.60） |
| **检测 F1**                | 2 × P × R / (P + R)                       | > 0.75                    |
| **遮挡目标召回率**         | TP_occluded / (TP_occluded + FN_occluded) | > 0.60                    |
| **检测延迟**               | 从帧输入到检测结果发布的时间（ms）        | < 100ms                   |

### 预测指标

| 指标                                 | 公式                                          | 目标值                          |
| ------------------------------------ | --------------------------------------------- | ------------------------------- |
| **ADE (Average Displacement Error)** | (1/T) × Σ‖p̂_t − p_t‖₂                         | 1s: <0.5m, 2s: <1.2m, 3s: <2.0m |
| **FDE (Final Displacement Error)**   | ‖p̂_T − p_T‖₂                                  | 3s: <3.0m                       |
| **遮挡场景 ADE**                     | 同 ADE，仅在 occlusion_level=heavy 子集上计算 | 1s: <0.8m                       |
| **覆盖率 (Coverage)**                | GT 轨迹在预测分布 2σ 范围内的比例             | > 0.85                          |

### 决策指标

| 指标                 | 公式                                                | 目标值 |
| -------------------- | --------------------------------------------------- | ------ |
| **碰撞避免率 (CAR)** | 避免碰撞事件数 / 总鬼探头事件数                     | > 0.90 |
| **平均预警提前量**   | mean(t_warning − t_trigger) over all events (秒)    | > 1.5s |
| **误报率 (FPR)**     | 无实际风险时发出 danger/emergency 警报次数 / 总帧数 | < 0.05 |
| **制动合理性**       | 减速度在合理范围 [0, 8] m/s² 内的比例               | > 0.95 |

### 系统指标

| 指标               | 公式                                   | 目标值  |
| ------------------ | -------------------------------------- | ------- |
| **端到端延迟**     | t_frontend_render − t_frame_input (ms) | < 300ms |
| **消息丢失率**     | 1 − (received_msgs / sent_msgs)        | < 0.01  |
| **降级触发正确率** | 正确触发降级 / 应触发降级              | > 0.95  |
| **系统吞吐量**     | 稳定处理帧率（Hz）                     | ≥ 10Hz  |

### Jetson TensorRT 部署注意事项

| 事项             | 说明                                                         |
| ---------------- | ------------------------------------------------------------ |
| **模型导出**     | PyTorch → ONNX → TensorRT engine；YOLOv8 用 `model.export(format='engine', device='0')` |
| **精度选择**     | 先用 FP16（速度提升 2-3x，精度损失 <1%）；如需进一步加速用 INT8 需标定数据集 |
| **输入尺寸固定** | TensorRT 需固定输入分辨率，建议 640×640；动态 batch 可选但增加复杂度 |
| **内存限制**     | Jetson Nano 4GB 共享内存；YOLOv8-nano + 轻量 GNN 约需 1.5GB，留足系统余量 |
| **散热**         | 持续推理 Jetson 会热降频；准备散热风扇 + 监控 `tegrastats`   |
| **JetPack 版本** | 确保 JetPack 版本与 TensorRT 版本匹配，建议 JetPack 5.1+     |
| **Python 版本**  | Jetson 上 Python 版本可能与开发机不一致，用 conda/venv 隔离  |

| ----------------- | ------------------------------------------------------------ | ------ |

## 附录 B：最容易失败的 5 个点与规避策略

### 1. DAIR-V2X 数据格式解析与坐标系转换

| 维度         | 详情                                                         |
| ------------ | ------------------------------------------------------------ |
| **失败表现** | 检测结果在 BEV 上位置完全错误；行人飘在空中或地下            |
| **根因**     | DAIR-V2X 有多套坐标系（相机/激光雷达/世界坐标），标定矩阵使用错误；图像坐标系 y 轴方向与 3D 坐标系相反 |
| **规避策略** | ① 第一天就写一个 `test_coordinate.py`：取标注中的 3D 坐标，投影回图像，检查是否落在 bbox 内 ② 画出 BEV 散点图目视确认行人/车辆分布是否合理 ③ 先只用 2D 检测 + 像素坐标，跑通链路后再切 3D |
| **发现时机** | Day 2 前端显示检测框时                                       |

### 2. MQTT 消息时序错乱导致决策闪烁

| 维度         | 详情                                                         |
| ------------ | ------------------------------------------------------------ |
| **失败表现** | 风险等级在 safe/danger 间快速跳变；制动指令反复下发/撤回     |
| **根因**     | MQTT QoS 0 不保证顺序；路侧检测延迟波动导致车端收到乱序帧；车端状态机无去抖 |
| **规避策略** | ① 所有消息携带 `frame_id`，车端丢弃 frame_id < 已处理最大值的消息 ② 风险等级加迟滞：升级（safe→danger）立即生效，降级（danger→safe）需连续 5 帧确认 ③ 使用 QoS 1 确保消息不丢（但仍需自己处理顺序） |
| **发现时机** | Day 3 车端决策对接时                                         |

### 3. 轨迹预测在目标 ID 跳变时崩溃

| 维度         | 详情                                                         |
| ------------ | ------------------------------------------------------------ |
| **失败表现** | 预测轨迹突然跳到另一个位置；ADE 指标异常大；程序偶发 KeyError |
| **根因**     | 简易追踪器在遮挡/重叠时丢失目标 → 重新分配 ID → 历史轨迹缓存与新 ID 不匹配 → 线性预测用了错误的历史点 |
| **规避策略** | ① 追踪器使用 IoU + 位置距离双重匹配，阈值宽松些（允许遮挡后重现） ② 轨迹缓存以 obj_id 为 key，ID 跳变时重新初始化缓存（不用旧数据） ③ 预测器检查历史点是否在合理范围内（连续帧位移 <2m），异常则重置 |
| **发现时机** | Day 4 轨迹预测上线时                                         |

### 4. 前端 3D 渲染与后端数据不同步导致"穿模"

| 维度         | 详情                                                         |
| ------------ | ------------------------------------------------------------ |
| **失败表现** | 前端行人模型穿过建筑物；车辆悬浮在空中；回放时画面抖动       |
| **根因**     | 前端 Three.js 坐标系（Y-up）与数据集坐标系（Z-up）不一致；前端渲染帧率与数据帧率不同步；Z 坐标未归零 |
| **规避策略** | ① 前端统一做坐标转换：`three_pos.set(data.x, data.z, -data.y)` ② 前端用插值平滑位置更新（lerp），不直接赋值 ③ 地面高度固定为 0，所有目标 Z 坐标钳位到地面 ④ 前端维护帧缓冲队列（3-5帧），按 frame_id 顺序消费 |
| **发现时机** | Day 2 前端对接时                                             |

### 5. 评测指标"虚高"——训练集和评测集场景过于相似

| 维度         | 详情                                                         |
| ------------ | ------------------------------------------------------------ |
| **失败表现** | val 集指标漂亮，但换到新 clip 或实体环境时性能断崖下降       |
| **根因**     | mini_split 的 train/val 来自同一路口同一时段，场景高度同质；检测模型过拟合于特定视角和光照 |
| **规避策略** | ① train/val 按路口或时段切分，不按随机帧切分 ② 保留 2-3 个完全不同路口的 clip 作为 held-out 测试集 ③ 评测时分别报告"同分布"和"跨分布"指标 ④ 使用预训练权重 + 少量微调，而非从头训练，降低过拟合风险 |
| **发现时机** | Day 6 评测时                                                 |
